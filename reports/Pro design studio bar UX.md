# Pros chunk look apart from tools

Professionals structure design and authoring bars by **separating global look preferences from ephemeral editing modes and from export helpers**, not by dumping every control into one unlabeled row. Theme, fonts, shell, and glass behave like Storybook/Radix **orthogonal globals** applied to the preview root; Paint and Move behave like Figma/Photoshop **armed tools** with secondary actions disclosed only while active; Usage and Copy stay in authoring chrome and never ship in product extracts. UIMi’s Design bar already sits outside the catalog canvas (the right industrial placement), but its flat chip-and-select strip still mixes three mental models—settings, modes, and actions—so it reads as a control dump. Making the bar feel intuitive means **four labeled chunks with separators** (Layout · Appearance · Tools · Catalog), distinct control types per bucket, Glass as a master appearance switch rather than a paint-like tool or a fifth palette, and progressive disclosure of Undo/Save/Clear, glass presets, and long helper sentences. Overflow should collapse by priority into one row plus menus—not wrap into multi-line “control lasagna.”

## Pros split chrome into look, tools, and export zones

Across Figma, Webflow, Framer, Sketch, Penpot, and Photoshop, **global appearance never shares an undifferentiated cluster with the tool that edits the canvas**. Figma UI3 moved mode switching and drawing tools into a floating bottom toolbar while selection appearance lives in a right properties panel—explicitly to stop “playing Tetris” in one mega-bar ([Figma Blog — Designing UI3](https://www.figma.com/blog/our-approach-to-designing-ui3/); [Figma Help — design tools](https://help.figma.com/hc/en-us/articles/360041064174-Access-design-tools-from-the-toolbar)). Webflow assigns top bar, canvas bar, left toolbar, and right Style/Settings/Interactions each a job; interface light/dark lives under the main menu and is documented as **controlling the Designer, not the published site** ([Webflow Help — Intro](https://help.webflow.com/hc/en-us/articles/33961260162323-Intro-to-Webflow); [Webflow — Light and dark themes](https://webflow.com/updates/light-and-dark-themes-across-webflow)). Sketch clusters insert and tools leftward and parks fills, borders, and effects in the Inspector ([Sketch Docs — The Toolbar](https://www.sketch.com/docs/interface-and-settings/the-mac-app-interface/the-toolbar/); [Sketch Docs — The Inspector](https://www.sketch.com/docs/interface-and-settings/the-mac-app-interface/the-inspector/)). Photoshop’s lasting recipe is left Tools for *what*, top Options for *settings of that tool*, and panels for fills—plus a Contextual Task Bar for next steps after a tool is chosen ([Adobe Help — tools and options](https://helpx.adobe.com/africa/photoshop/using/using-tools.html)). Material Design 3 allows **separate toolbars for different action kinds** (for example undo versus edit tools) with stylistic distinction on large screens ([Material Design 3 — Toolbars](https://m3.material.io/components/toolbars/guidelines)).

Design-system sandboxes harden the same split for theme specifically. Storybook exposes theme as a **global toolbar dropdown** that re-renders decorators around the story iframe—never as a control inside the story ([Storybook Docs — Toolbars & globals](https://storybook.js.org/docs/essentials/toolbars-and-globals)). Atlassian and Carbon follow the same manager-chrome pattern so the picker stays playground-only ([Atlassian Design — Storybook addon](https://atlassian.design/components/storybook-addon-design-system/code); [Carbon theme Storybook PR](https://github.com/carbon-design-system/carbon/pull/3989)). shadcn’s theme customizer lives on a docs themes page beside a live preview, then **Copy code**—chrome around canvas, not shippable app shell ([shadcn/ui Discussion #9353](https://github.com/shadcn-ui/ui/discussions/9353); [shadcn/ui Theming](https://ui.shadcn.com/docs/theming)). Tokens Studio keeps export/theme checkboxes in the Figma plugin panel, completely separate from design frames ([Tokens Studio — Export Using Themes](https://docs.tokens.studio/figma/export/themes)). UIMi’s `.uimi-studio` aside already matches this **chrome around canvas** pattern; the intuition gap is not placement relative to preview, but **lack of internal zoning** once controls share one horizontal strip.

Mature kits also keep **palette and modes on orthogonal axes** instead of minting combined theme names. Radix Themes puts `appearance`, `accentColor`, `panelBackground` (`solid` | `translucent`), radius, and scaling on one Theme wrapper ([Radix Themes — Theme API](https://www.radix-ui.com/themes/docs/components/theme)). Atlassian lists light/dark alongside density and typography as separate theming dimensions ([Atlassian — Design tokens](https://atlassian.design/foundations/tokens/design-tokens)). Tokens Studio maps Theme Groups to Variable Collections and Themes to Modes that share token names ([Tokens Studio — Export Using Themes](https://docs.tokens.studio/figma/export/themes)). UIMi’s `data-uimi-palette` versus `data-uimi-glass` already follows that model; the Design bar should **visually reinforce** it by parking Glass with Appearance, not beside Paint/Move as a peer chip.

## Flat chip rows collapse three interaction types into one language

Apple HIG groups toolbar items by **function and frequency**, minimizes groups, and keeps leading/center/trailing roles distinct; Settings guidance parks infrequently changed options in Settings and keeps task-specific options in the task UI without stuffing Settings into a crowded toolbar ([Apple HIG Toolbars mirror](https://apple.raintree.technology/topics/toolbars); [Apple HIG Settings mirror](https://apple-docs.everest.mt/docs/design/human-interface-guidelines/settings/)). NN/g progressive disclosure shows a few important options first and chunks advanced features so users can ignore irrelevant areas; chunking uses proximity, background, rules, and white space—not a hard “seven item” cap on always-visible recognition UIs ([NN/g — Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/); [NN/g — Chunking](https://www.nngroup.com/articles/chunking/)). Fluent and Chrome toolbar guidance mark logical groups with separators and `role="group"` labels, and encode **toggle buttons** (`aria-pressed`) differently from **action buttons** that must never carry pressed state ([Chrome — Toolbar UI guide](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-components/toolbar); [Fluent CommandBar migration](https://storybooks.fluentui.dev/react/?path=%2Fdocs%2Fconcepts-migration-from-v8-components-commandbar-migration--docs)).

Control-type choosers across Primer, Toyota DX, Accor, and AIA converge: **dropdowns** for five-plus or long-labeled exclusive options; **segmented controls** for two to five short, equal, immediately applied choices; a **switch** for a single binary setting; **chips** for filters—not as the default chrome for mixed setting+mode+action rows ([Primer — Segmented control](https://primer.github.io/design/components/segmented-control/); [Toyota DX — Segmented control](https://dx-playbook.toyota-europe.com/cds/components/forms/segmented-control/); [AIA Design — Chip](https://design.aia.com/component/chip)). Material’s vibrant toolbar scheme signals a **temporary change in page behavior such as edit mode**—a different visual weight from calm settings chrome ([Material Design 3 — Toolbars](https://m3.material.io/components/toolbars/guidelines)). Apple’s Reduce Transparency is a **master display preference**, not another wallpaper or theme ([Apple Support — iPhone display](https://support.apple.com/guide/iphone/change-display-colors-iph3e2e1fb0/ios)). Figma UI3 found that icon-only, tooltip-dependent naming slowed discovery and invested in **visible labels that match aria-labels** ([Figma Blog — Designing UI3](https://www.figma.com/blog/our-approach-to-designing-ui3/)). NN/g likewise rejects tooltip-only names for ambiguous icons and keeps persistent toolbar microcopy extremely short, moving explanatory sentences into on-demand tooltips while never hiding task-critical instructions only in hover ([NN/g — Icon Usability](https://www.nngroup.com/articles/icon-usability/); [NN/g — Tooltip Guidelines](https://www.nngroup.com/articles/tooltip-guidelines/)).

UIMi’s current inventory—shell segmented control, Theme/UI/Headings/Usage selects, Paint and Move Off clusters with Undo/Save/Clear and status meta, Glass Off|On with inline explanatory sentences—already exceeds “few primary options” progressive-disclosure guidance when laid flat. Using the **same chip styling** for Glass Off/On, Paint Off, and Paint Undo/Save/Clear collapses a setting, a mode, and actions into one visual language—the anti-pattern UX Patterns Guide and Apple HIG warn against when unrelated actions share space “just because they share a row,” or when selection segments mix with action-performing controls ([UX Patterns Guide — Toolbar](https://uxpatternsguide.com/patterns/toolbar/); [Apple HIG — Segmented controls mirror](https://apple-docs.everest.mt/docs/design/human-interface-guidelines/segmented-controls/)). Inline copy such as “On = use glass · Off = solid theme” is good first-run scent but **too long for a dense horizontal bar**; status strings like unsaved counts belong only while a mode is active.

## Overflow collapses by priority instead of wrapping the bar

There is **no validated magic integer** for when a bar must collapse. Apple, Material, Fluent, and Android all encode **width-driven overflow with explicit priority**: center or secondary items collapse first; trailing essentials and More stay visible; least-used actions leave the bar first ([Apple HIG Toolbars mirror](https://apple.raintree.technology/topics/toolbars); [Material M2 — Top app bars](https://m2.material.io/components/app-bars-top); [Android — App bar actions](https://developer.android.com/develop/ui/views/components/appbar/actions); [Fluent CommandBar types](https://app.unpkg.com/office-ui-fabric-react@7.181.0/files/lib/components/CommandBar/CommandBar.types.d.ts)). PatternFly surfaces at most two primary actions and parks the rest in a kebab; NN/g notes that overflow is recognizable but **hiding key actions hurts usability**, especially on large screens where chrome would have fit ([PatternFly — Toolbar](https://www.patternfly.org/components/toolbar/design-guidelines/); [NN/g — Overflow menus](https://www.nngroup.com/videos/overflow-menu-icons/); [NN/g — Content-to-chrome](https://www.nngroup.com/articles/content-chrome-ratio/)). Figma answered small/split screens with Minimize UI and collapsible panels rather than wrapping chrome; Webflow simply requires a **1268px** Designer minimum rather than turning authoring into a phone layout ([Figma Blog — Designing UI3](https://www.figma.com/blog/our-approach-to-designing-ui3/); [Webflow Help — Intro](https://help.webflow.com/hc/en-us/articles/33961260162323-Intro-to-Webflow)). Penpot and Photoshop densify via **flyouts and nesting**, not multi-row wrap ([Penpot 2.18 release notes](https://penpot.app/release-notes/2-18-born-this-way); [Adobe Help — tools](https://helpx.adobe.com/africa/photoshop/using/using-tools.html)).

For a studio bar like UIMi, a practical heuristic—aligned with “minimize groups,” not Miller’s seven—is **about three to five always-visible primary chunks**, with one master control visible per group and secondary actions behind mode-on disclosure or a More menu. Prefer **one horizontal row plus overflow** over wrapping. A priority order that matches frequency guidance: keep Theme, Glass master, and active Paint/Move toggles longest; collapse Catalog/Usage and secondary fonts first when width shrinks; park glass presets, gear, Undo/Save/Clear, and counts before parking the mode switch itself. Authoring chrome remains desktop-first without copying Webflow’s hard floor blindly for every embedded preview.

Export and framework Usage belong in authoring surfaces the way shadcn Copy, DaisyUI generator copy, Storybook Source, and Tokens Studio Export do—adjacent to theme pickers in the playground, always producing tokens/markup, **never embedding the picker into the artifact** ([shadcn/ui Pro Themes](https://pro.shadcn.co/docs/themes); [daisyUI themes](https://daisyui.com/docs/themes/); [Storybook — Toolbars & globals](https://storybook.js.org/docs/essentials/toolbars-and-globals)). Kits mark playground-only chrome explicitly: Storybook tags such as `autodocs` + `!dev`, DaisyUI `themecontroller: false` / `exclude: themecontroller`, MUI’s written warning that docs density themes must not ship, and UIMi’s `data-uimi-kit="authoring"` ([Storybook — Tags](https://storybook.js.org/docs/writing-stories/tags); [daisyUI config](https://daisyui.com/docs/config/); [MUI — Density](https://mui.com/material-ui/customization/density/)). Usage tabs should switch **snippet dialect only**; emitted code keeps product `data-uimi-*` attrs and strips the studio aside.

## What UIMi’s Design bar should do next

The bar should read left to right as **Layout · Appearance · Tools · Catalog**, with a visible section label or `role="group"` name and a vertical separator between buckets—synthesized from Apple grouping, NN/g chunking, Figma tools-versus-properties, Material/Fluent overflow, and Chrome/APG group labeling ([APG — Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/); [Chrome — Toolbar guide](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-components/toolbar)).

| Bucket | Controls | Pattern | Always visible |
| --- | --- | --- | --- |
| Layout | Shell Sidebar \| Navbar | Segmented control | Yes |
| Appearance | Theme, UI, Headings | Labeled dropdowns with dynamic closed titles (e.g. current palette name) | Yes for Theme; fonts may fold into Appearance menu when narrow |
| Appearance | Glass Off \| On | Switch or two-segment control—not action chips, not a palette | Master only |
| Appearance secondary | Glass presets, Clear, gear/modal, counts | Popover after Glass On | No |
| Tools | Paint, Move | Toggle buttons with `aria-pressed` and distinct armed styling when On | Toggles only |
| Tools secondary | Undo, Save, Clear, Unsaved, pick counts | Reveal when that mode is On | No |
| Catalog | Usage HTML/React/Vue/Svelte | Dropdown, visually separated from Appearance | Yes, or first into overflow when width-constrained |

**Glass stays in Appearance**, modeled on Reduce Transparency and Radix `panelBackground`: one master On/Off for whether glass surfaces are in play; presets refine after On and never appear as equal parallel “themes” ([Apple Support — Reduce Transparency](https://support.apple.com/guide/iphone/change-display-colors-iph3e2e1fb0/ios); [Radix — Theme API](https://www.radix-ui.com/themes/docs/components/theme)). Paint and Move stay in Tools as mutually exclusive or independently armable modes with Material-style edit-mode emphasis while On. Theme/UI/Headings/Usage keep dropdowns; Shell keeps a segmented control. Microcopy shrinks to one-to-two-word labels; move the Glass explanation into a tooltip such as “When on, selected surfaces use liquid glass; theme colors stay the same.” Accessibility: name the Design region, name each group, separate with `role="separator"`, use `aria-pressed` only on true toggles—and treat a full `role="toolbar"` carefully if `<select>`s remain in the same arrow-key roving group ([APG — Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/); [MDN — toolbar role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/toolbar_role)).

Anti-patterns to drop: scope soup in one unlabeled flex row; treating palette and Paint as peer chips; icon salad with tooltip-only names; always-wrap multi-line bars; priority-free overflow; shipping `.uimi-studio` as if it were the theme; exposing Regular + Clear + Chrome + Thick as equal always-on toggles; inventing “Apricot LG” versus “Apricot solid” palettes.

## Conclusion

The industry pattern is not a prettier chip strip—it is **scope zoning**: look preferences stay scannable and calm, tools announce when they change the canvas, and export stays labeled as authoring dialect. UIMi already chose the hard part correctly (aside chrome, orthogonal palette×glass attrs, `data-uimi-kit="authoring"`). Intuition now hinges on making those scopes **visible in the bar’s structure and control types**, so authors feel three jobs—preview look, edit kit marks, copy a framework snippet—rather than one undifferentiated settings drawer.

What remains uncertain is exact overflow priority and whether Usage belongs in-bar versus copy FAB chrome; neither Apple nor NN/g publishes a validated control-count cutoff, and no public frequency telemetry for UIMi’s Design bar exists yet. A short usability pass that asks whether users find Glass without confusing it with Theme, and whether they discover Paint’s Undo/Save only after disclosure, will validate the four-bucket map faster than another taxonomy debate.
